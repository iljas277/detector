# Локальный поиск объектов в видео

Локальная страница для быстрого просмотра объектов в видео: выберите файл, введите нужные объекты через запятую (например, `машина, человек`) или приложите фото объекта, нажмите «Найти объекты», затем смотрите или скачивайте MP4 с рамками. Поля геоданных и настройки анализа убраны из страницы. Серверный API и CLI для старого режима поиска конкретной цели сохранены.

Быстрый режим проверяет 2 кадра в секунду и создаёт видео с этой частотой кадров, без звука. Модель OWLv2 ищет только выбранные типы объектов: русские названия из словаря переводятся в английские запросы, другие типы можно указать по-английски. За один запуск можно указать до 8 типов. Фото ищется консервативным сопоставлением изображения на нескольких масштабах: оценка у рамки означает сходство рисунка, а не вероятность правильного ответа. Это лучше подходит для того же объекта с похожего ракурса; другой ракурс или освещение могут привести к пропуску. Небольшие и коротко появляющиеся объекты могут быть пропущены. Просматривайте результат глазами; оценка качества на размеченном наборе данных не проводилась.

## Запуск

Нужны Python 3.12, `ffmpeg` и `ffprobe`. На Linux без CUDA:

```bash
cd detector
python3.12 -m venv .venv
.venv/bin/python -m pip install 'torch==2.6.0+cpu' --index-url https://download.pytorch.org/whl/cpu
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python -m video_search.cli init
.venv/bin/python -m video_search.cli weights download
```

`weights download` — отдельная явная загрузка модели. Видео и фото не отправляются во внешние сервисы. Для своей папки данных задайте `VIDEO_SEARCH_DATA` до запуска; пример переменных в `.env.example`. Без весов поиск по названию завершится понятной ошибкой; поиск только по фото работает без OWLv2. `device=auto|cpu|cuda`; реально выбранное устройство показывается в задаче и CLI. Если запрошена недоступная CUDA, fallback не скрывается — задача падает с ошибкой.

Откройте два терминала:

```bash
cd detector
.venv/bin/python -m video_search.cli worker
```

```bash
cd detector
.venv/bin/uvicorn video_search.api:app --host 127.0.0.1 --port 8000
```

Интерфейс: <http://127.0.0.1:8000>. Загрузите видео, укажите объекты или фото и нажмите «Найти объекты». После обработки откройте результат или скачайте MP4 и ZIP с данными. На одной машине запускайте один worker. API и worker — отдельные процессы; API не выполняет inference. Если порт 8000 занят, выберите другой (например, `--port 8765`) и откройте соответствующий адрес.

Если локальные процессы уже запущены и код был обновлён, выполните `./restart-local.sh` из этой папки. Скрипт останавливает только процессы этого проекта, запущенные из этой папки, и поднимает API на порту 8765 вместе с worker.

## Быстрый API и ZIP

`POST /api/quick/analyze` принимает `multipart/form-data`: обязательный `file` (видео), `objects` (названия через запятую) и/или `reference_image` (фото, до 20 МБ). Достаточно одного из двух способов указать цель. Если переданы оба, результат должен совпасть и с названием, и с фото. Для поиска по фото лучше приложить кадр с крупным объектом без лишнего фона. Бэкенд может дополнительно передать `start_utc` в ISO 8601 с часовым поясом, пару `latitude`/`longitude`, `accuracy_m` и `telemetry_json` — JSON-массив образцов `[{"time_s":0,"latitude":55.7,"longitude":37.6,"accuracy_m":4}]`. Координаты относятся к камере или дрону. Неподтверждённые координаты объекта API не вычисляет.

Ответ загрузки — `{"job_id": 1, "cached": false}`: анализ выполняется асинхронно. Статус и ссылки доступны через `GET /api/quick/jobs`. После завершения `GET /api/quick/jobs/{job_id}/archive` возвращает ZIP с `annotated.mp4`, `detections.json` и, при поиске по фото, `reference.jpg`. В JSON для каждого проверенного кадра есть время в исходном и выходном видео, `timestamp_utc` при наличии `start_utc`, координаты источника при наличии геоданных, метки, оценки и рамки. Если бэкенд не передал время или геоданные, соответствующие значения остаются `null`.

С Docker Compose (если Docker установлен):

```bash
docker compose build
docker compose run --rm api python -m video_search.cli weights download
docker compose up
```

Compose использует тот же `./data` и CPU-сборку PyTorch. В этой среде Docker Compose не проверялся.

## CLI без интерфейса

Сначала проверьте модель на одном изображении, затем на коротком видео:

```bash
.venv/bin/python -m video_search.cli target 'Автомобиль' --mode category --prompt 'a photo of a car' --confirm-prompt
.venv/bin/python -m video_search.cli image 1 /path/to/frame.jpg --threshold 0.2 --device cpu
.venv/bin/python -m video_search.cli import /path/to/clip.mp4 --kind drone --flight-id test-flight
.venv/bin/python -m video_search.cli analyze 1 1 --scan sampled --step 1 --refine-step 0.2 --threshold 0.2 --device cpu --wait
.venv/bin/python -m video_search.cli episodes
.venv/bin/python -m video_search.cli export --format json --output /tmp/episodes.json
.venv/bin/python -m video_search.cli export --format csv --output /tmp/episodes.csv
.venv/bin/python -m video_search.cli export --format mp4 --episode-id 1 --output /tmp/episode.mp4
```

Для поиска по фото:

```bash
.venv/bin/python -m video_search.cli target 'Белая машина' --mode visual_similarity
.venv/bin/python -m video_search.cli reference 2 /path/to/frame.jpg --bbox 150 600 230 730
.venv/bin/python -m video_search.cli image 2 /path/to/other-frame.jpg --threshold 0.5
```

Измените ID по фактическому выводу CLI. Несколько положительных образцов объединяются правилом **максимального score по совпадающим рамкам** с NMS. Отрицательные образцы отсекают положительную рамку, когда перекрытие не меньше 0.5 IoU и отрицательный score не ниже положительного. Порог `category` и порог `visual_similarity` отдельны. Для `category` сохраняется score текстовой детекции; для `visual_similarity` — `sigmoid(max logit)` image-guided модели, а не пересчитанная библиотекой прозрачность рамки. Это не вероятность идентичности. Одинаковое число для разных режимов нельзя считать одинаковой достоверностью.

`full` декодирует каждый кадр; `sampled` сначала проверяет кадры с шагом, затем более плотно обрабатывает окна ± шаг возле кандидатов. Короткое появление можно пропустить в sampled. Отсутствие находки не доказывает отсутствие объекта. `--tile-size 640` включает перекрывающиеся тайлы, перевод координат в исходный кадр и NMS. Размер, пороги, устройство, шаги и контекст сохраняются в записи запуска. ByteTrack из Supervision связывает рамки внутри файла; движение дрона может разрушить трек или вызвать смену ID. Компенсация движения камеры в MVP отсутствует. Разрывы между реальными наблюдениями не выдаются за подтверждённые наблюдения; интерполированных рамок нет.

Эпизод хранит `observed_start_s`/`observed_end_s` отдельно от границ клипа с контекстом (`start_s`/`end_s`). Для одиночной находки наблюдаемые метки одинаковы, но клип содержит контекст. Время кадра берётся из PTS и приводится к началу видеопотока. Абсолютное время появляется только если при импорте указана дата с часовым поясом. Исходный файл не перемещается и не удаляется, а копия с SHA-256 хранится в `VIDEO_SEARCH_DATA/originals`.

## Метаданные и экспорт

CLI принимает `--start-utc '2026-10-04T12:00:00+03:00'`, `--latitude`, `--longitude`, `--accuracy-m`, `--telemetry /path/to/sidecar.json`. JSON sidecar — массив объектов, CSV — таблица с колонками `time_s,latitude,longitude,accuracy_m`. `time_s` — секунда от начала записи; ближайшая телеметрия используется, если расстояние по времени не больше 2 с. `sync_error_s` показывает это расстояние. Точность синхронизации, кроме него, неизвестна. Координаты относятся к камере/дрону, не к объекту; геолокация объекта по одной рамке не вычисляется.

JSON/CSV экспортируют ID запуска, видео, источника, цели и трека, версию цели и модели, наблюдаемые/контекстные интервалы, UTC и координаты при наличии, статус проверки и правило ранжирования. CSV колонки перечислены в `video_search/service.py` (`CSV_COLUMNS`); `location` записывается как JSON-строка, неизвестные значения — пустые поля. Данные отдельных детекций доступны по `/api/episodes/{id}/detections`. MP4 перекодируется через libx264, поэтому начало не ограничено ключевыми кадрами исходника. Из-за дискретности кадров фактическая длительность может отличаться на один кадр; для внешней точной синхронизации проверьте PTS экспортированного файла. Подборка скачивается ZIP с `episodes.json` и MP4. Результаты завершённого запуска остаются на его версии цели; изменение цели создаёт следующую версию. Ключ кэша учитывает SHA-256 видео, версию цели, модель, revision и параметры. Новая цель приводит к новому анализу.

При ошибке или отмене задача сохраняет состояние. Повтор:

```bash
.venv/bin/python -m video_search.cli jobs
.venv/bin/python -m video_search.cli retry JOB_ID
```

Повтор удаляет только неполные результаты этого запуска и ставит его обратно в очередь. После аварийной остановки worker помечает прерванную задачу `failed` при следующем старте. Миграция первой версии — `create_all` при `init`; для существующей БД изменение схемы требует явной миграции или новой папки данных. Не выставляйте этот MVP напрямую в интернет: API рассчитан на доверенный локальный компьютер, без учётных записей. Максимум загружаемого видео по умолчанию 2048 МиБ; имена файлов нормализуются. Команды FFmpeg вызываются без shell.

## Оценка качества

Создайте JSON вида:

```json
{
  "videos": [{"video_id": 1, "duration_s": 60, "split": "test", "source_kind": "drone"}],
  "episodes": [{"video_id": 1, "target_id": 1, "mode": "category", "start_s": 10.0, "end_s": 12.0,
    "boxes": [{"time_s": 11.0, "bbox": [100, 80, 140, 130], "tolerance_s": 0.2}]}],
  "job_ids": [1]
}
```

```bash
.venv/bin/python -m video_search.cli evaluate /path/to/annotations.json --temporal-iou 0.5
```

Один эпизод сопоставляется с одной разметкой при IoU временных интервалов ≥ порога. Отчёт даёт precision/recall, ложные эпизоды на час, среднюю абсолютную ошибку границ и средний IoU рамок по размеченным кадрам, отдельно для `stationary_camera`/`drone` и `category`/`visual_similarity`. Нужны реальные, отдельно размеченные видео с целями и без них. Подбор параметров и тест разделяйте по всей съёмке/источнику, не по соседним кадрам. `null` означает, что данных для метрики нет. Отчёт включает CPU/GPU, разрешение, настройки и время обработки часа видео. Без разметки показатели качества не заявляются.

## Модели, версии, лицензии

- Основной адаптер: [OWLv2 в Transformers](https://huggingface.co/docs/transformers/model_doc/owlv2), [официальный пример image-guided detection](https://huggingface.co/docs/transformers/tasks/zero_shot_object_detection), веса [`google/owlv2-base-patch16-ensemble`](https://huggingface.co/google/owlv2-base-patch16-ensemble/tree/57beb61adb5abda3de4a9796bc35ae60bc4b9802) revision `57beb61adb5abda3de4a9796bc35ae60bc4b9802`, Apache-2.0. Локальная команда загрузки пишет SHA-256 каждого файла в `data/models/owlv2/manifest.json`. Код использует `Owlv2ForObjectDetection`, `Owlv2Processor`, `image_guided_detection`, официальный post-process для текста и пересчёт координат padded image для поиска по фото. Версия конвейера входит в ключ кэша. `torch==2.6.0`, `transformers==4.51.3`, `supervision==0.25.1`, `av==15.1.0`; остальные точные версии в `requirements.txt`.
- На имеющемся дроновом кадре image-guided OWLv2 дал много крупных ложных рамок. Это согласуется с [зарегистрированным сообщением о проблеме image-guided детекции](https://github.com/huggingface/transformers/issues/27821), но само по себе не доказывает общую неисправность модели. OWL-ViT с тем же crop также вернул неверную рамку на весь кадр; он не включён в проект. Для конкретных камер нужны разметка, подбор образцов/порогов и отдельная оценка до использования находок как достоверных.
- [YOLO-World](https://github.com/AILab-CVC/YOLO-World) изучен как кандидат для category. Официальный код под GPLv3; в MVP не установлен и не используется. [Статья](https://arxiv.org/abs/2401.17270).
- [LocateAnything-3B](https://huggingface.co/nvidia/LocateAnything-3B) по текущей карточке имеет некоммерческую лицензию NVIDIA; опубликованный путь принимает изображение и текстовый запрос, но не документирует visual-prompt путь для этих весов. Необязательный экспериментальный кандидат, в MVP не установлен. [Проект](https://research.nvidia.com/labs/lpr/locate-anything/), [код](https://github.com/NVlabs/Eagle/tree/main/Embodied).

Это локальный MVP, не гарантия поиска конкретного экземпляра и не замена оценке на ваших записях. Нет RTSP, автоматического управления дроном, поиска действий, геолокации объекта, компенсации движения камеры и многопользовательской авторизации.

## Фактически проверено в этой среде

- Python 3.12.3, FFmpeg 6.1.1, PyTorch 2.6.0+cpu; CUDA не обнаружена. Все основные зависимости установлены; 4 unit-теста прошли.
- Веса OWLv2 закреплённого revision загружены; SHA-256 `model.safetensors`: `e1e130b9e404cf91a75ad45644c1da9d7fa5284085eecc864266a6923efb99e7`.
- На отдельном кадре дронового видео OWLv2 в `category` при пороге 0.15 выдал рамки видимых автомобилей. На клипе 4.994 с `category`, sampled 1 с + refinement 0.5 с, порог 0.2 и CPU завершился с 45 эпизодами. Это сырые находки, не оценка качества; порог даёт много спорных эпизодов.
- На другом клипе 3 с без видимого автомобиля, `category` и порог 0.3 дали 0 эпизодов. Пороги разных проверок различаются.
- Поиск по crop автомобиля на одном кадре выполнился, но при пороге 0.5 дал 64 рамки, многие явно ложные; короткий тест `visual_similarity` на видео при пороге 0.7 сохранил 40 эпизодов. Оценки этого режима нельзя использовать как признак идентичности или качества без ручной разметки. Это подтверждает необходимость калибровки под ваши съёмки.
- JSON, CSV, перекодированный MP4 и ZIP-подборка созданы и прочитаны. Для клипа с запросом 1.04 с фактическая длительность по ffprobe составила 1.073 с. HTTP-маршруты здоровья, целей, видео, кадра, проверки результата и подборки ответили успешно. Новый простой интерфейс открыт в браузере: просмотр готового MP4 работает. Быстрый анализ пятисекундного дронового видео завершился, создал H.264 MP4 1200×900 длительностью 5 с с рамками. При общем поиске на одном кадре видны правильно обведённые машины и ложная метка «boat» на другой конструкции. Повторный запуск только для «машины» создал отдельный MP4 с рамками автомобилей без меток других классов; повторная загрузка с тем же выбором вернула готовый результат из кэша. JavaScript прошёл синтаксическую проверку.
- В изолированной тестовой БД прогнан короткий ролик с `objects=машина`, фото автомобиля, `start_utc` и телеметрией. ZIP содержит `annotated.mp4`, `detections.json`, `reference.jpg`; время первого кадра переведено в UTC, координаты записаны как положение источника. Совмещение текста и фото оставило одну рамку автомобиля на первом кадре. Проверка вызовов маршрутов API в процессе подтвердила кэш и получение ZIP. Полный HTTP-тест через `TestClient` не запускался: в виртуальном окружении нет необязательного пакета `httpx`.
- В предыдущем поиске только по фото для полосатого тента 10 кадров содержали 50 ложных рамок и пропускали сам тент. После замены поиска в быстром режиме на сопоставление изображения тот же ролик дал 10 рамок на тенте в 10 кадрах; на другом ролике совпадений не было. Исправленный MP4 сохранён как `data/annotated/job-10.mp4`. Автоматические тесты: 8 пройдено. Это проверка на конкретных роликах, а не оценка точности на всём наборе съёмок.
- В отдельной временной БД проверены снимок версии цели при постановке задачи, новый запуск после правки цели и повторная постановка отменённой задачи. Повтор того же завершённого видеозапуска вернул запись из кэша.
